# Phase 7B — Game-Wide Module Analysis

Phase 7B turns the Phase 7A disc inventory into a game-level reverse-engineering workspace. It reuses the existing executable analyzer, Allegrex/VFPU disassembler, Splat project generator, and NID linker rather than adding a second analysis stack.

## Scan-only vs full analysis

Use `game` when you only want to inventory a PSP ISO/CSO and extract executable candidates:

```bash
pspdisasm game GAME.iso game_intake
```

Use `game-project` when you want those candidates analyzed automatically:

```bash
pspdisasm game-project GAME.iso game_decomp
pspdisasm game-project GAME.cso game_decomp --nid-db psp_nids.csv
```

`game-project` first performs the same Phase 7A scan/extraction, then processes each executable candidate in deterministic disc-path order.

## Module statuses

Every candidate receives one explicit status in `metadata/game_analysis.json`.

### `analyzed`

The extracted candidate is a usable decrypted ELF/PRX. Phase 7B:

- runs executable analysis;
- runs Allegrex/VFPU disassembly;
- generates a normal per-module Splat workspace;
- includes the module in the game-wide import/export linker pass.

### `needs_decryption`

The candidate is a recognized encrypted `~PSP` container. Phase 7B preserves its container/module metadata and warnings but does not guess or bypass PSP cryptography. It is not disassembled, given a Splat project, or supplied to the cross-module linker.

### `failed`

The candidate could not complete parsing, disassembly, or project generation. The failure is recorded on that module while remaining modules continue. Missing global analysis engines remain fatal because a requested full-analysis workflow cannot be performed correctly without them.

## Output layout

Per-module projects mirror the original logical disc paths, avoiding basename collisions and preserving provenance:

```text
game_decomp/
├── metadata/
│   ├── disc.json
│   ├── param_sfo.json
│   ├── game_analysis.json
│   ├── module_links.json
│   └── propagated_symbols.json
├── modules/
│   └── PSP_GAME/
│       ├── SYSDIR/EBOOT.BIN
│       └── USRDIR/... extracted PRX candidates ...
└── projects/
    └── PSP_GAME/
        ├── SYSDIR/
        │   └── EBOOT.BIN/
        │       ├── splat.yaml
        │       ├── target.bin
        │       ├── config/
        │       ├── metadata/
        │       ├── asm/
        │       ├── src/
        │       ├── assets/
        │       └── reports/
        └── USRDIR/
            └── MODULE.PRX/
                └── ... normal per-module project ...
```

All mirrored paths pass containment checks before use; absolute paths, parent traversal, and resolved paths outside the intended output root are rejected.

## Game-level reports

### `metadata/game_analysis.json`

The authoritative whole-game summary contains:

- source image, image format, title, disc ID, and selected boot path;
- every executable candidate and its status;
- extracted path and per-module project path when applicable;
- function, symbol, reference, and string counts for analyzed modules;
- module-local warnings;
- normalized cross-module linking results;
- game-level warnings inherited from disc intake.

### `metadata/module_links.json`

This is the normalized `ModuleLinkAnalysis` generated once across all successfully analyzed decrypted modules. Existing Phase 6B rules remain authoritative:

- exact `(library, kind, NID)` identities;
- unique-provider links only;
- ambiguous providers produce warnings rather than guessed links;
- external NID database names take precedence when strong;
- meaningful uniquely linked local names can propagate with confidence `0.95`;
- autogenerated names are not treated as authoritative local names.

### `metadata/propagated_symbols.json`

This convenience report contains only the game-wide propagated symbol suggestions from the linker.

## NID databases

`game-project` accepts the same repeatable `--nid-db` option as `project` and `link`:

```bash
pspdisasm game-project GAME.iso game_decomp \
  --nid-db psp_nids.csv \
  --nid-db game_specific_nids.json
```

Later databases take precedence for duplicate exact identities, matching the existing Phase 6B behavior. The same database list is also passed into each generated per-module project.

## Failure isolation

A malformed or unsupported secondary module does not prevent analysis of valid modules elsewhere on the disc. Its record becomes `failed`, its error text is preserved in deterministic metadata, and successfully analyzed modules still reach the global linker pass.

This isolation does not apply to missing global analysis engines: `EngineUnavailableError` remains fatal so the command never pretends a partial environment is a successful full analysis.

## Python API

The public package exports:

```python
from pspdisasm import generate_game_project

result = generate_game_project(
    "GAME.iso",
    "game_decomp",
    nid_databases=["psp_nids.csv"],
)
```

`GameProjectResult` reports the output/report paths plus total, analyzed, encrypted, and failed module counts. Detailed game/module/link information is persisted in the normalized JSON reports.

## Current boundary

Phase 7B completes automatic game-wide executable/module orchestration, but it intentionally does not add:

- PSP cryptographic decryption;
- GZIP/KL4E/2RLZ recovery of encrypted `~PSP` bodies;
- recursive analysis of arbitrary resource archives or proprietary containers;
- game-wide texture/model/audio conversion;
- reinjection of game-wide propagated names into every already-generated module `config/symbols.txt`;
- automatic PSP compiler/version identification;
- ZSO/DAX disc input;
- parallel module analysis.

Resource-manager reconstruction and recursive game-data discovery remain later phases rather than being inferred from filenames or signatures in Phase 7B.
